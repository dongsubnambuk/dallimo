# 서버 성능 개선 결과

명세 31장(성능 테스트 계획)과 54장(벤치마크 양식)을 따랐다. 같은 데이터 · 같은 부하로 개선 전후를 쟀다 (결정 로그 70항). 측정 도구와 재현 방법은 `backend/dallimo-server/perf/README.md`, 원본 수치는 `backend/dallimo-server/perf/results/*.json`이다.

## 1. 코스 랭킹 · 내 순위 · 코스 상세

- **문제:** 기록 10만 건 코스에서 랭킹 p95가 1.5초였다. 내 순위는 4.2초, 코스 상세는 1.5초였다.
- **원인 1 (랭킹):** 전체 기간 랭킹이 요청마다 그 코스의 공식 기록 10만 건을 사용자별로 묶었다.
  - `EXPLAIN ANALYZE`에서 목록 쿼리는 10만 행을 읽고 423ms가 걸렸다.
  - 쓰는 인덱스 `(course_id, user_id, duration_seconds)`에 기간 조건 열 `created_at`이 없었다. 그래서 행마다 표를 다시 읽었다.
  - 전체 인원 수 쿼리(`COUNT(DISTINCT user_id)`)도 10만 행을 읽고 329ms가 걸렸다.
  - 내 순위 API는 이런 집계를 3번(인원 · 순위 · 주변 목록) 돌렸다.
- **원인 2 (코스 상세):** performance_schema로 쿼리별 시간을 보니 "이번 주 달린 사람 수"가 가장 컸다.
  - 이 쿼리가 코스의 Run 10만 건을 모두 읽었다(평균 301ms).
  - 인덱스 `(course_id, verification_status)`에 `status` · `started_at`이 없었다.
- **해결 1:** 명세 23.1장에 적힌 사용자별 최고 기록 projection `tbl_course_user_best`(V22)를 만들었다.
  - 공식 기록을 넣는 트랜잭션 안에서 그 사용자 한 줄만 원본에서 다시 계산한다.
  - 전체 기간 랭킹 · 인원 · 내 순위와 코스 1등 기록 · 완주자 수가 이 표를 `(course_id, best_seconds, user_id)` 순서로 읽는다.
- **해결 2:** `(course_id, status, started_at, user_id)` 인덱스(V23)를 추가했다. 그 쿼리가 414ms에서 3.3ms가 됐다.
- **결과:**
  - 랭킹 p95 1,540 → 106ms
  - 내 순위 4,183 → 336ms
  - 코스 상세 1,477 → 206ms
  - 처리량 8.9~21배
- **정합성:**
  - projection이 원본 `GROUP BY`와 같은지(같은 시간이면 먼저 세운 기록) 테스트로 확인한다.
  - 전체 테스트를 MySQL 8.4 · MariaDB 11.4 Testcontainers에서 통과했다.
  - DB 트리거는 쓰지 않았다. 운영 MySQL은 바이너리 로그가 켜져 있어(MySQL 8 기본값) 일반 계정으로 트리거를 만들 때 권한 오류가 날 수 있어서다.

## 2. 주변 코스

- **문제:** 반경 3km 조회 p95가 495ms, 10km는 720ms였다.
- **원인:** 범위 안 후보 약 4,800개를 요청마다 JPA 엔티티로 전부 만든 뒤 메모리에서 거리순으로 정렬했다. 그리고 20개만 썼다.
  - 후보 조회는 표 전체(1만 행)를 읽었다. 인덱스 `(start_lat, start_lng)`에 공개 조건 열이 없었다.
- **해결:**
  - 후보는 id · 출발점만 읽는다.
  - 거리순으로 자른 한 페이지(20개)만 엔티티로 불러온다.
  - 출발점과 공개 조건 열을 모두 담은 인덱스(V24)로 표를 읽지 않게 했다(후보 조회 20.5 → 5.2ms).
- **결과:**
  - 3km p95 495 → 246ms, 처리량 2.4배
  - 10km p95 720 → 279ms, 처리량 2.8배
  - 이 중 3km 495 → 431ms는 1번의 코스 통계 개선 몫이고, 431 → 246ms가 이 변경의 몫이다.

## 3. GPS 업로드

- **문제:** 러너 1명 기준 묶음 하나가 p50 47.5ms였다. 러닝이 길어질수록 느려졌다(앞 10묶음 43ms → 뒤 10묶음 55ms).
- **원인 1:** 묶음마다 "1부터 빠짐없이 이어진 마지막 seq"를 그 러닝의 점 전체를 자기 조인해서 다시 셌다. 7,200점 러닝에서 이 쿼리 하나가 24.6ms였다.
- **원인 2:** MySQL 드라이버가 점 60개 INSERT를 한 문장씩 따로 보냈다(`rewriteBatchedStatements` 꺼짐). 운영 compose도 MySQL 드라이버를 쓴다.
- **해결:**
  - 확인한 seq를 `tbl_run.contiguous_seq`(V21)에 저장하고, 다음 묶음은 그 뒤부터만 센다.
  - 점은 지우지 않아서 저장한 값까지는 계속 이어져 있다.
  - 드라이버 옵션을 켰다.
- **결과 (러너 1명):**
  - 묶음당 p50 47.5 → 20.6ms
  - 뒤 10묶음 54.9 → 21.0ms (이제 러닝 길이와 상관없다)
- **결과 (러너 20명 동시):** 처리량 3,902 → 6,082 point/s
- **나눠 본 몫:** 드라이버 옵션만 켰을 때 러너 1명 p50은 37.0ms였다. 동시 20명은 거의 그대로였다(286 → 267ms). 동시 처리량을 올린 것은 seq 계산 변경이다.

## 4. 기록 목록 썸네일 (머지 전에 막은 느려짐)

- **문제:** 기록 목록에 경로 썸네일을 넣는 기능(`feat/history-thumbnail`)을 머지하기 전에 쟀다. 2시간 러닝 20개가 한 페이지면 썸네일 쿼리 하나가 1,315ms(예열 뒤 622ms) 걸렸다.
- **원인:** 러닝마다 점 41개를 고르려고 창 함수(`ROW_NUMBER` · `COUNT OVER`)를 썼다.
  - 그래서 점 14만 개를 모두 정렬했다.
  - `EXPLAIN ANALYZE`를 보면 인덱스 대신 GPS 점 표 전체(46만 행)를 읽었다.
- **해결:** 러닝마다 첫 · 마지막 seq를 인덱스로 구한다. 그 사이를 고르게 나눈 seq 41개만 `(run_id, seq)` 인덱스로 읽는다.
- **결과:** 같은 러닝 20개에서 0.2ms + 7.5ms. 점 820개만 읽는다.
- API 부하 측정이 아니라 같은 데이터에서 SQL 실행 시간(`EXPLAIN ANALYZE`)을 비교했다.
